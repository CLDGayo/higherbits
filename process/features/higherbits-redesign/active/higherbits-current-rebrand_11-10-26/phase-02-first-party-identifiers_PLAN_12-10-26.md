## Data Flow and Failure Modes

1. Accepted analytics consent permits legacy-first nonempty ID selection, canonical fallback, then one generated ID only if both reads succeed and neither holds an ID. Attempt both writes independently and read back both exact values. Anonymous capture must verify aliases still equal the selected in-memory identity before duplicate lookup and again after the await before insert. Any read/write/readback error or mismatch suppresses anonymous lookup/insertion; no new fallback identity after failure. A consent-generation token invalidates captures across revoke/reaccept, in addition to checking current consent before query and insert. Cleanup attempts both deletions even if the first throws; physical deletion cannot be guaranteed if storage denies it. Signed-in accepted capture retains user_id payload, omitted anon_id and existing duplicate behavior; anonymous storage failure must not suppress that signed-in path. No-consent and in-flight revocation apply to both paths. Preserve the development early exit and activity/event/query values.
2. The MCP-only helper exports `readOnboardingState(): OnboardingState | null`, `writeOnboardingState(state: OnboardingState): boolean`, and `clearOnboardingState(): boolean`. Types remain compatible with existing client exports; type-only imports must create no runtime consumer cycle. Read candidates independently without a write-availability probe; validate non-null non-array object, six existing step enum values, IDE cursor/cline/windsurf/null, OS mac/windows/linux, and an array containing only existing step enum values. Require all four fields; tolerate additional properties without inventing, dropping or transforming serialized fields. Return valid legacy, else valid canonical, else null. Write one serialization to both independently; return true only if both reads verify exact serialized bytes. Clear attempts both independently and returns true only when both absent on readback. No throwing through consumer UI; false does not discard readable state or claim successful synchronization. Consumers control auth/timing; helper does not authorize users or run provider operations.
3. Onboarding waits for loaded live Clerk identity before storage initialization/save, applies URL-step and detected-OS precedence, then dual-persists. Signed-out with stale initial identity clears/reset state and cannot rewrite on subsequent effects or URL changes. Console reads actual helper at its existing mount boundary and synchronizes valid selected stored state with the helper without altering serialized values; failed synchronization cannot discard the restored IDE. UI retains valid IDE/cursor default and detected OS; its enclosing layout still owns access control. Neither consumer gains a testing seam.
4. Subscribe selection uses the nonempty canonical/legacy pair at import; the request guard checks all three effective audience presences and existing API key before provider construction. Fixtures reset module imports for each synthetic environment. Provider error/status handling is untouched.
